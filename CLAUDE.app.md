# FLASHApp

FLASHApp's own guidance, imported by the template-owned `CLAUDE.md` (which describes the framework).

## What This Is

**FLASHApp** is a Streamlit web application for **top-down proteomics** with the OpenMS FLASH* tool family. It is built on the [OpenMS streamlit-template](https://github.com/OpenMS/streamlit-template). `app.py` registers one analysis section (⚡️ **Top-down analysis**) and the developer-only FLASHIda section:

- **Top-down analysis** (⚡️, one workflow, `content/TopDown/`) — spectral deconvolution of every run (FLASHDeconv: raw MS ion peaks → neutral monoisotopic masses, with isotope/charge resolution and FDR scoring) and, with **Identify proteoforms** on and a protein database, tag-and-track identification (FLASHTnT matches short sequence "tags" against the database to identify proteoforms (PrSMs), with target/decoy FDR; FLASHAnnotator annotates their fragments). Off, a run is deconvolved only (MS1-only or intact-mass runs, samples without a fitting database).
- **FLASHIda** (🧠) — developer feature of the local app only: registered in `app.py` when `src/flashida.py::available()` (local app + developer mode unlocked; the unlock is remembered in `<local workspaces>/.developer-mode` until Lock). Acquisition (`content/FLASHIda/FLASHIdaAcquisition.py`): a table of runs (`src/render/ida_runs.py`, `<workflow_dir>/ida-runs.json`), each a raw file name with its method: a `.json` file in the **method folder** (Instrument PC, param `method-folder`; `src/flashida_folder.py`, Streamlit-free), picked in the run's searchable dropdown and stored as `method_file`; FLASHIda gets the file as it is when its run starts (the workflow re-reads it then). Setting the folder saves the built-in and the user's presets into it once (never overwriting) and moves methods a table still keeps in its runs (`{name, preset, method}`, before the folder) to files (`adopt_embedded`). `.favorites.json` in the folder lists favorites (☆ beside a run's dropdown), first in every method choice. **📝 New or edit method** opens the Method dialog (start from any method or edit one; the keys by section, every key, or the JSON) and saves to the folder. Per run: 📋 copies its method (**Paste into selection** gives it to the ticked runs), ↑/↓ move it, ⧉ duplicates it with the next free name (R1 → R2). Below the table: the summed `global.duration` and the expected end, **Export JSON** (runs with their method files and methods, version 2; importing writes methods the folder lacks), **CSV** (row, raw file name, method), **Import** (that JSON, version 1 too, or the raw file names of any Xcalibur `.sld` with one method for all; appended or replacing the table, duplicate names kept and marked) and **Add runs by pattern** (prefix_date_sample_comment_replicate_suffix, samples one per line with their own `; comment=` / `; replicates=`, either order, a wash run with the **Wash** method every n runs, live preview); that logic is in `src/flashida_sequence.py`. The keys, defaults and checks come from FLASHIda's own schema, `assets/flashida/method.schema.json` (copy a newer one from FlashIDA's `docs/site/` when it gains keys; until then a key the schema does not know is kept, listed as unknown (`flashida_method.unknown_keys`) and passed to FLASHIda, which checks it, so it never blocks a run); `src/flashida_method.py` (Streamlit-free) reads it, checks a method with `jsonschema` and keeps the presets: built-in ones in `assets/flashida/presets.json`, the user's per instrument PC in `<local workspaces>/.flashida-presets.json`. Running, `IdaWorkflow` reads the newest `.sld` in the raw folder (`flashida.sequence_rows`), reports in `ida-status.json` which runs it schedules, and starts Flash.exe with a run's method for each new raw file named in the table (also when the sequence does not list it); other raw files are left alone. It remembers the method's `runtime.log_dir` and a live Viewer (`src/render/ida_live.py`, an `st.fragment(run_every=…)`) that re-reads a run folder's `scan_commands.tsv`, `scan_results.tsv`, `identification.tsv` and `pooled_identification.tsv` (`src/parse/ida_log.py`) and shows the survey masses with the chosen precursors, the precursors and the scans commanded for each.

The heavy lifting is done by **TOPP command-line tools** (`FLASHDeconv`, `FLASHTnT`, `DecoyDatabase`) shipped in the Docker image; the app drives them, parses their output into pandas DataFrames, caches them per workspace, and renders them with **openms-insight** components (`Table`, `Heatmap`, `DeconvolvedSpectrum`, `Plot3D`, `SeriesPlot`, `ProteinSequenceView`).

## Commands

```bash
# Run locally (online_deployment=false in settings.json → always "local" mode)
streamlit run app.py local

# Unit tests (pytest; uses fakeredis, needs pyopenms importable)
pytest tests/ -v
pytest tests/test_selection_clear.py -v                 # single file
pytest tests/test_selection_clear.py::test_name -v      # single test

# Lint (errors-only; mirrors .github/workflows/pylint.yml, which runs on `main`)
pylint $(git ls-files '*.py') --errors-only --disable=C0103,C0114,C0301,C0411,W0212,W0631,W0602,W1514,W2402,E0401,E1101,F0001,R1732

# Docker (full image with OpenMS + TOPP tools + openms-insight built from source)
docker build -f Dockerfile --no-cache -t flashapp:latest --secret id=github_token,env=GITHUB_TOKEN .
docker run -p 8501:8501 flashapp:latest          # → http://localhost:8501
# Dockerfile.arm is the linux/arm64 variant (swaps miniforge installer to aarch64).
```

Python is pinned to **3.11** (matches the Docker runtime). `GITHUB_TOKEN` is required at build time to fetch OpenMS resources.

### openms-insight

The viewers need `openms_insight` importable. It comes from PyPI (`openms-insight>=0.6.0` in `requirements.txt`) in the Docker images, the desktop apps and local installs. A feature that needs an unreleased openms-insight change may build it from a branch for a while, but a release requires a published version. The unit tests do not import it.

`.streamlit/config.toml` → `developmentMode = false` for production builds.

## Architecture

### The data pipeline (the core mental model)

Every sub-app follows the same path; understanding it requires reading `src/Workflow.py`, `src/parse/`, `src/workflow/FileManager.py`, and `src/render/`:

```
mzML upload ──► WorkflowManager.execution()
                   └─ executor.run_topp('FLASHDeconv' / 'FLASHTnT' / 'DecoyDatabase')
                        └─ writes out_deconv.mzML, annotated.mzML, *.tsv, *.feature, *.msalign
                            └─ src/parse/* turns those into pandas DataFrames
                                └─ FileManager.store_data(dataset_id, key, df)  ──► workspace cache
                                                                                       │
Viewer page ◄── render_grid() (src/render/render.py) ◄── reads cached results + layout ◄──┘
                   └─ one openms-insight component per layout cell (shared StateManager)
```

- **Workflows:** `src/Workflow.py` defines `TopDownWorkflow` (the former FLASHDeconv and FLASHTnT workflows, merged; `TagWorkflow`/`DeconvWorkflow` are aliases for queued jobs of older builds) and `QuantWorkflow`, all subclasses of `WorkflowManager` (`src/workflow/WorkflowManager.py`). Each implements `upload()`, `configure()`, `execution()`, `results()`. `execution()` runs TOPP tools, stores every output file via `FileManager.store_file()`, then calls the parsers. `TopDownWorkflow` runs `FLASHDeconv` per run and, with `identify` on, `DecoyDatabase` → `FLASHTnT` → `FLASHAnnotator`. It keeps the FLASHTnT workflow's name and folder (`flashtnt/`, its params and the `flashtnt` presets); the MS data of the former `flashdeconv/` workflow is listed by reference (`external_files.txt`) on first use (`adopt_legacy_inputs`).
- **Parsers (`src/parse/`):** `deconv.py::parseDeconv`, `tnt.py::parseTnT` are the entry points. The mzML→DataFrame heavy lifting lives in `masstable.py` (`parseFLASHDeconvOutput`, `parseFLASHTaggerOutput`) using a **multiprocessing pool**; `tag_resolution.py` maps tags ↔ proteoforms.
- **Renderers (`src/render/`):** `insight_data.py` turns the cached results into the lazy frames each component is built from (one row per mass, signal peaks per mass, best hit per spectrum, …; Streamlit-free, tested in `tests/test_insight_data.py`). `render.py::render_grid` builds one openms-insight component per layout cell; the components of a grid share a `StateManager` (identifiers `scan`, `mass`, `protein`, `pscan`, `tag`, `aa`, `sequence`, `feature_group`), cleared when the grid switches dataset. Each component's preprocessed cache lives in `<cache>/insight/<dataset>/`; its cache id hashes the source results (size, mtime) and the code of `render.py`/`insight_data.py`, so editing either rebuilds the caches. `compression.py` is still used by the parsers.

### Pages and the Layout Manager

Each sub-app's pages (in `content/<SubApp>/`, `content/TopDown/` for the merged workflow) are registered in `app.py`. The Viewer arranges its components with the template's **view bar** (`src/layout_manager`, `view_bar`): one segmented control with the ready-made views **Deconvolution**, **Native** and **Lysate** (`topdown_layout.presets`), then the user's own, **+** to make a view (a copy of the current one, its starting point switchable), More and ✏️ **Customize views** (order the views, tick which are in the bar, edit rows from a searchable palette; ready-made views are read-only, **Duplicate to edit**; up to five experiments side by side or one below the other). Views are saved in `<workspace>/layouts/viewer.json` (`topdown_layout.views_path`); the layouts saved before the view bar are adopted once (`adopt_saved_layout`): one saved by the former Edit layout dialog (`'topdown_layout'` in the cache) becomes the current view ("My layout" unless it equals a ready-made one), and those the two former Viewers saved (`'layout'` deconvolution, `'flashtnt_layout'` identification) become "My deconvolution layout" and "My identification layout". Until the user picks a view, the current one follows the first run (`default_view`: the adopted layout of its kind, else Deconvolution for a run deconvolved only, Native or Lysate by its `-native` setting), and a ready-made view of a labelled run gets the reporter components (`view_rows`). Every component of an experiment shares one Insight `StateManager`, so a picked scan, mass or proteoform stays picked when the view changes. A comparison of runs gets a view bar of its own (`quant_view.view_selector`, `<workspace>/layouts/comparison.json`): the ready-made views, in this order, **Quantification** (the default, `quant_view.default_view`), **Identification** (what each run identified and what the runs share, then proteoforms across the runs → the PrSMs of the picked one in every run (`quant_form`) → the sequence view and annotated spectrum of the picked PrSM (`quant_prsm`), drawn from its run's own results with a run `StateManager` of their own; no conditions needed), **QC: label-free** (the consensus features: feature map, intensity of detected and matched values, the feature table and the picked feature run by run (`quant_feature`); match between runs, loading, correlation, CV, the comparison steps) and **QC: TMT, iTRAQ** (the reporter ions of the labelled runs: intensity and ratio per label, labels found per spectrum, the run's reporter table and ions; channel loading, correlation, PCA, CV, the comparison steps); a comparison shows only the QC of its kind (`quant_view.comparison_presets`), and the Identification components that need PrSMs (`QUANT_IDENTIFICATION_ONLY`, `needs: identification`) lock the Identification view of a comparison of runs that were not identified, whose + opens **Add identification to the N runs** (`missing_analysis.comparison_options`: their files locked, their deconvolution reused, the runs compared again) (`quant_view.presets`; saved views files get this order once, `_reorder_presets`; the counts are in the Streamlit-free `src/quant/qc.py`, what a comparison was made from (its stored runs, found by id or by the mzML of their `analysis_settings`, the PrSMs of `identifications_tsv`, the reporter ions, the consensus features) in the Streamlit-free `src/quant/sources.py`, the plots in `src/render/comparison_plots.py`; saved views naming the former Label-free and TMT, iTRAQ views get Quantification, `migrate_views`), and the user's own; the layout saved with the former comparison Edit layout dialog (`'quant_layout'`) becomes "My comparison layout" and stays the default of every comparison until a view is picked.

- One Viewer (`TopDownViewer.py`) shows every run in one combined view (`tool='topdown'` in `render_grid`): the catalog is `TOPDOWN_COMPONENTS`, both kinds together. Identification tables set the `scan` selection too (beside `pscan`), so spectra, the mass table and the tag table follow either the scan table or an identification; the sequence view shows the proteoform of an identified run, else the sequence set in the view; identification components on a run deconvolved only say so. One layout, **`'topdown_layout'`** (`src/render/topdown_layout.py`). Until one is saved, each experiment starts from the default of its run: the layout a former Viewer saved for its kind (**`'layout'`** deconvolution, **`'flashtnt_layout'`** identification), else the deconvolution default, or the Native/Lysate default for an identified run by its `-native` setting (`sample_type.of_result`). It is JSON-importable/exportable.
- **Views a run was not processed for** (`src/render/missing_analysis.py`): identification components need `identification`, reporter components `isobaric` (`needs` in `catalog.py`). The view bar marks the views a shown run cannot fill with a **+**, and the grid draws a note with **Add …** in place of such a component (`render_grid(..., on_missing=...)`). Both open a dialog with one choice. Identification is added to the run itself (**Add identification to <run>**, `missing_analysis.add_identification`): Describe experiment opens with the run's settings (`TopDownWorkflow.start_from` with the FLASHDeconv and FLASHTnT parameters stored with the run and its input file; `EXAMPLE_INPUTS` names the input files of the example runs), its file locked (`same_files`), identification on and the quantification as the run had it, and FLASHDeconv kept (`keep`): `execution()` copies the run's stored deconvolution (`_reused_deconvolution`, `_copy_deconvolution`) and runs only DecoyDatabase, FLASHTnT and FLASHAnnotator, so only the database and the identification settings can be changed; the new run is kept next to the old one. Isobaric labels, which FLASHDeconv measures, are added by processing more files with these settings and the labels switched on. **Add analysis** beside the experiment selector (`missing_analysis.add_files`; for a comparison, with the runs it compares, `quant_view.comparison_runs`) extends any run or comparison the same way; when the runs join as they are, Describe experiment shows their files apart (`files_key`), and the Run button at the end of the page starts the run (`run_page`).
- **Process more files** (`missing_analysis.more_files_settings`) compares the added files with the shown run: it switches label-free quantification on when the run had none, and when the run was processed with what the new start needs (`analysis_settings`, stored with every run by `quant.run.run_record`) only the added files are processed and the run joins the comparison as it is (`start_from(adds_to=...)`, read in `execution()` by `follow_up_info()`, `quant.run.reusable_runs`); otherwise its file is processed again with them. The Viewer then shows that comparison (`quant_view.added_comparison`).
- **The sequence of a run that was not identified** is set in the sequence view's own **Change sequence** dialog (there is no separate page). `render.py::_deconv_sequence` saves it with its fixed modifications to the `'sequence'` dataset; a saved sequence unlocks the `Internal fragment map` component in the Layout Manager. Without one the view starts empty.
- **Editing an identified proteoform**: the identification sequence view's pencil button (openms-insight `edit_identifier`) lets the user change the sequence and modifications of the shown proteoform, and its reset button goes back to the search result. `src/render/proteoform_edits.py` (Streamlit-free) keeps the edits per proteoform in the dataset's `proteoform_edits` result; `render.py::_edited_sequence_view` renders an edited proteoform from its own cache (`<cell>-<tool>-edited-<proteoform>`), with fragment masses of the unmodified edited sequence (the view adds the modifications and localizes them). An edit's nonce is applied once per session (`_proteoform_edit_nonce`); never clear the edit selection, since every view holds it and would send it back (a rerun loop). Older openms-insight builds without `set_edit_identifier` simply show no pencil.
- **Fragment ions on the spectra**: every sequence view publishes the fragment ions it matched to the `fragment_matches` selection (`FRAGMENT_MATCHES_IDENTIFIER` in `render.py`), with the spectrum they were matched on (`spectrum_key_column`: `scan_idx` for identifications, `index` for a deconvolved run); the raw, deconvolved and tag spectra mark and label them on that spectrum. Ion types, an edited sequence and its modifications update the marks. Needs an openms-insight with `DeconvolvedSpectrum.set_fragment_matches_identifier` (`FRAGMENT_MARKS`); older builds show unmarked spectra. The Native and Lysate defaults show both spectra below the sequence view.
- **The analysis choice** (`src/analysis.py`, Streamlit-free): `identify` (on/off), the sample type (Native/Lysate, the `flashtnt` presets, applied by the **Sample** control; `sample_type.is_on` reads the flag, whose checkbox holds the ini text `'true'`/`'false'`) and `quantification` (`none` | `label-free` | `isobaric`, falling back to the former `compare-runs` switch) with `isobaric-plex`. Six analyses result. `TopDownWorkflow.analysis_section()` draws them in the **Your analysis** box above the parameters (the page calls it before `show_parameter_section()`); `configure()` only draws the tabs that follow from them. The Native/Lysate preset buttons are hidden (`_no_preset_buttons`, module-level: the workflow object is pickled for its run).
- **Isobaric labels** (`src/quant/isobaric.py`, Streamlit-free): FLASHDeconv runs with `-iq:type <plex>` and `-out_quant`; `read_quant` reads the reporter table (stored per run as `isobaric_dfs`, with `isobaric_plex`), the channel table (channel, sample, condition) lives in `<workflow_dir>/isobaric-channels.tsv`, and `build` turns all runs of a start (fractions of one labelled set) into the comparison contract per level (feature: spectra within 10 ppm; proteoform/protein: FLASHTnT PrSMs at q ≤ 0.01; a native PrSM without any mass is a feature of its own). `src/quant/run.py::compare_isobaric` stores it with `kind: 'isobaric'` in the manifest, so `QuantSession.isobaric` makes the comparison speak of samples instead of runs. The Viewer adds `reporter_table`/`reporter_ions` (`ISOBARIC_COMPONENTS`) to the default of a labelled run (`topdown_layout.with_reporters`).
- **User Guide** (`content/user_guide.py` + `.md`): a line `@video name.mp4 | caption` embeds `static/videos/name.mp4`. The four instruction videos are Playwright recordings of the app with caption overlays.
- **Workflow pages** are two steps before the Viewer (its menu entry and links say **Explore results**; the file stays `TopDownViewer.py`). **Run analysis** at the end of Describe experiment (`wf.show_run_button`) opens Run analysis and starts the run there at once; a finished run offers **Explore results** (`show_execution_section(results_page=...)`). `<Tool>Configure.py` (Describe experiment; `analysis_section()` picks the runs and the database with `select_input_file(..., upload=...)`, whose **📂 Browse** dialog lists the files by folder and adds new ones, so there is no upload page; `configure()` draws one numbered tab per step the chosen analysis runs: **Samples and groups** only with quantification, identification tabs only with identification; the Sample (Native/Lysate preset) control is always shown; `analysis.preset_note` warns when a preset sets settings of a step the analysis does not run, except that a sample preset only notes that its identification settings wait for identification, since deconvolution only (DDA) and label-free without identification are supported analyses) and `<Tool>Run.py` (Run analysis). Output of FLASHDeconv/FLASHTnT run elsewhere is added on the Viewer (**Add tool results**, `src/render/tool_results.py`). Each opens with `page_intro` and ends with `next_steps` from `src/common/guide.py`.
- **Comparing runs** (`src/quant/`, `src/render/quant_view.py`, `src/render/quant_cells.py`): with **Quantification: Label-free** on, FLASHDeconv runs with `-quant` and, after the per-file loop, `src/quant/run.py` runs FLASHQuantConsensus over the stored runs (FLASHTnT adds the PrSMs as `-in_id` and, when the tool has it, `-out_id`, the proteoform of each consensus feature). `src/quant/contract.py` reads the output into the contract shared with the quant unification work (a long table per level: feature, proteoform, protein); `src/quant/session.py` stores it as a dataset `comparison_<time>` in the same cache (`quant_*` names, `tool` in `quant_manifest`) and runs the comparison chain of `src/parse/quant_compare.py` per level, cached by a stamp of the design and settings. The Viewer lists it as **Comparison: N runs (date)**; selecting it replaces the grid with the comparison grid (`QUANT_COMPONENTS`, its views as above, the former layout under `quant_layout`; `quant_view.migrate_layout` moves the former `flashtnt_quant_layout` there) and adds **Edit comparison** (conditions, level, analysis settings). The conditions start from the workflow's Samples table (`experimental-design.tsv`).

### Workspaces & FileManager

State lives in per-session **workspaces** (`enable_workspaces: true`, `workspaces_dir: ".."` → `../workspaces-FLASHApp/`). `FileManager` (`src/workflow/FileManager.py`) is the single gateway to the workspace's `cache/`: `store_file`, `store_data`, `get_results`, `result_exists`, `get_results_list`, `get_files`, keyed by a `dataset_id` (typically `<filename>_<timestamp>`). Demo workspaces are seeded from `example-data/workspaces/` (`demo_workspaces` in `settings.json`).

### Parameters

`ParameterManager` (`src/workflow/ParameterManager.py`) persists widget state to JSON and generates TOPP `.ini` files. `configure()` exposes TOPP tool parameters via `self.ui.input_TOPP('FLASHDeconv', exclude_parameters=[...], custom_defaults={...})`. **Widget keys must match keys in `default-parameters.json`.** `presets.json` holds named parameter bundles (`test_parameter_presets.py` guards this).

### Deployment & runtime (`entrypoint.sh`, `k8s/`)

The container entrypoint starts **Redis** + one or more **RQ workers** (queue `openms-workflows`) + Streamlit. When `STREAMLIT_SERVER_COUNT > 1`, it runs N Streamlit instances behind an **nginx** load balancer with sticky-cookie session routing. `QueueManager` (`src/workflow/QueueManager.py`) offloads `execution()` to RQ when `online_deployment` is set. The entrypoint is written to tolerate **Apptainer/Singularity** read-only rootfs (all runtime state goes under `$RUNTIME_DIR`, default `/tmp/opendiakiosk`). `k8s/` is a kustomize base + `overlays/prod` deploying to namespace `openms` as `ghcr.io/openms/flashapp:latest` behind nginx/traefik ingress; `clean-up-workspaces.py` runs via cron for periodic GC.

### CI (`.github/workflows/`)

- `build-and-test.yml` — multi-arch (amd64 + arm64) Docker build → merged manifest, kustomize/kubeconform lint, and **container smoke tests** under apptainer / nginx-on-kind / traefik-on-kind, then publishes images + an ORAS SIF to GHCR. (Its "test" jobs are deployment smoke tests, **not** pytest.)
- `unit-tests.yml` — the pytest suite. `pylint.yml` — lint. `build-desktop-app.yaml` — one run builds the Electron app for all three platforms, from the template's unified build. The `openms` job (`openms.yml`) builds OpenMS `t0mdavid-m/OpenMS@FDmerge` (it has FLASHAnnotator) from source on Windows, macOS and Linux, once per commit (cached by SHA; a released version such as `3.5.0` would be downloaded instead). One `build` job, a matrix over Windows / macOS (arm64) / Linux, then runs the same bash steps everywhere: `electron/scripts/stage-openms.sh` (the built package as `OPENMS_PACKAGE`), `stage-python.sh` plus the openms-insight wheel and `polars-lts-cpu`, copy the app, `package.sh` (NSIS / signed and notarized dmg (when the `MACOS_CERTIFICATE`/`APPLE_*` secrets exist) / AppImage, named `<INSTALLER_NAME>-Setup.exe`, `-macOS-arm64.dmg`, `-Linux-x86_64.AppImage` while the app is `APP_NAME` FLASHApp), then `install-app.sh`, `smoke-payload.js`, `smoke-app.js` and `e2e.js --scenario tests/e2e/electron-workflows.js`. On a release every installer is attached as an asset, then `publish-web-image` runs `build-and-test.yml`. The Quickstart's download buttons (`src/common/installers.py`) link the installers of the latest release. `ghcr-cleanup.yml` — registry GC.
- `template-sync.yml` — weekly merge of the streamlit-template (`template` in `app.yaml`); conflicts in files listed under `sync.app_owned` keep FLASHApp's side. Merge those PRs with a merge commit, never squash, or the next sync conflicts again. `auto-merge.yml` and `.github/CODEOWNERS` form the review queue (`docs/review-queue.md`).

## Agent rules for FLASHApp

The template's *Agent operating rules* (in `CLAUDE.md`, which arrives with the template sync) apply here. What they mean for FLASHApp:

- **FLASHApp owns** the top-down science and its viewer: `src/Workflow.py`, `src/analysis.py`, `src/parse/`, `src/render/`, `src/quant/`, `src/flashida*.py`, `content/`, presets, parameter names and the files in `sync.app_owned` of `app.yaml`. Changes there are FLASHApp PRs (base `develop`).
- **To the template first**: anything under `src/workflow/`, `src/common/`, `src/layout_manager/`, `src/data_import/`, `src/sync/`, the Dockerfiles, `docker/`, `k8s/base`, `k8s/components`, `electron/`, `.github/` or `.claude/`, even when FLASHApp is the only app that needs it today (make it an option there). The layout manager and the view bar came from FLASHApp and now live in the template; change them there.
- **To openms-insight**: changes to the components the viewer is built from (`Table`, `Heatmap`, `DeconvolvedSpectrum`, `Plot3D`, `SeriesPlot`, `ProteinSequenceView`, their selection, zoom, fragment marks and edit identifiers). `src/render/` only builds the data and configures the components; a missing generic feature is an openms-insight PR, not a workaround in `render.py`.
- **To OpenMS**: the algorithms. Deconvolution, tagging, identification, annotation and quantification are done by the TOPP tools `FLASHDeconv`, `FLASHTnT`, `FLASHAnnotator`, `FLASHQuantConsensus` and `DecoyDatabase`; a new output, option or fix belongs in those tools (the desktop build uses `t0mdavid-m/OpenMS@FDmerge`), and the parsers read what they write. pyOpenMS stays the glue (reading mzML and TSV output, small conversions).
- **To FlashIDA** (`t0mdavid-m/FlashIDA`): the acquisition itself and its method keys. FLASHApp only writes methods and starts and reads FLASHIda; a new method key or acquisition behaviour is a FlashIDA change first.
- **Screenshots** for a viewer change show the affected views with the example workspace (deconvolved, identified and compared runs where it applies), in light and dark theme when colors change.
- **Release**: `requirements.txt` may point at an openms-insight dev wheel or branch between releases; before a FLASHApp release it must require a published PyPI version that holds every openms-insight change FLASHApp uses.

## Conventions & gotchas

- **`app.py` sets multiprocessing start method to `spawn`** (polars + Unix fork are incompatible) and imports `pyopenms` early (required for the Windows build). Don't remove these.
- **Vendor input:** FLASHDeconv and FLASHTnT accept Thermo `.raw` and Bruker timsTOF `.d` (`MS_DATA_TYPES` in `src/Workflow.py`). `execution()` converts them with `self.executor.convert_to_mzml()` (from the streamlit-template): FileConverter + ThermoRawFileParser for `.raw` (mono in the Docker images, .NET on Windows, `FileConverter` in the Windows `TOPP_TOOLS`), `src/python-tools/bruker_to_mzml.py` (timsrust + pyOpenMS) for `.d`. Converted mzML is cached in `<workflow_dir>/converted-mzML/`. Online, a `.d` is uploaded zipped.
- **Import from a link** (`src/data_import/`, from streamlit-template #428): the upload page gets a section that imports files from a link (HTTPS incl. presigned, public S3/Swift folders such as CSC Allas, OneDrive/SharePoint, Zenodo, Figshare; tar/zip listed in place) into the matching `upload_widget()` folder, as a background process reporting through `<workflow_dir>/link-import/`. Online, an SSRF guard refuses non-public addresses. Toggled by `data_import` in `settings.json`.
- **Running workflows locally needs the TOPP binaries** (`FLASHDeconv`, `FLASHTnT`) on `PATH` — they ship only in the full Docker image. The upload/viewer/download paths work on pre-computed result files without them.
- **Windows packaged build:** `run_app.py` + `run_app_temp.spec` (PyInstaller). A `windows` arg in `sys.argv` triggers a working-directory `chdir` in `page_setup()`.
- Pages start with `page_setup()` from `src/common/common.py`, which initializes the workspace, sidebar, and params; call `save_params(params)` at the end. Use `show_fig()` / `show_table()` for consistent display.
- **Light and dark theme**: `.streamlit/config.toml` defines `[theme.light]` and `[theme.dark]` without `theme.base`, so the app follows the OS color scheme (switch under ⋮ → Settings). `show_fig()` runs figures through `follow_app_theme()`; call it yourself before a direct `st.plotly_chart`. The Vue component reads the active theme from Streamlit's render args. Logos: `*-light.svg` (white tile, dark text) for the light theme, `flashapp-icon.svg` / `*-white.svg` (dark tile, white text) for the dark theme, picked by `st.context.theme.type`.
- Decorate `configure()` / page sections with `@st.fragment` for partial reruns.
- Workflow display names map to lowercase-hyphenated keys ("FLASHTnT" → workflow dir / preset keys); TOPP params use colon paths (`tag:min_length`).
